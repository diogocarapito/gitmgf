# Decisions log

D1–D10 are in TECH_SPEC §23. Deviations and implementation choices made while building the MVP:

| # | Decision | Reason |
|---|---|---|
| D11 | gettext msgids are the European Portuguese strings; only an `en` catalogue exists (`app/locales/en`). PT renders msgids directly. | PT-PT is the primary language and copy is written in context in the templates (TECH_SPEC §11.4 already uses PT msgids). `tests/test_i18n.py` fails on any untranslated or fuzzy EN entry. |
| D12 | OAuth uses Authlib's PKCE/token primitives with a **sync** httpx client, not Authlib's async Starlette client. State + PKCE verifier live in the signed `gitmgf_oauth` cookie (itsdangerous, 10 min). | Keeps every route handler synchronous (D2) and avoids Authlib's deprecated httpx integration. |
| D13 | CSRF is enforced by a global FastAPI dependency (`deps.csrf_protect`) rather than body-reading middleware; middleware only issues the cookie. | The dependency shares Starlette's cached parsed form with the handler, so the body is read once (multipart included). Behaviour matches TECH_SPEC §6.4. |
| D14 | Post-redirect messages use `?flash=<key>` mapped to translated strings (`labels.FLASH`). | No flash cookie, so the cookie table in Privacy §6 stays exact. |
| D15 | Emails are rendered when queued and stored in `email_outbox.body_text/body_html`; one gettext template per email (`templates/emails/<name>.txt`, HTML generated from it) instead of `.{lang}.txt` files. Added `next_attempt_at` for backoff. | The sender needs no template context; one template per message keeps PT/EN in the same catalogue. |
| D16 | Certification detail fields are server-rendered for every catalogue item and shown/hidden by `app.js`; there is no `/me/cert-fields/{code}` endpoint. | Same no-JS behaviour as the spec (all fields shown, ignored if unchecked) without a round trip per toggle. |
| D17 | `reports.locale` stores the reporter's language. | Acknowledgement and outcome emails go out in the language the report was filed in. |
| D18 | Legal placeholders resolve from site setting `legal.<KEY>`, falling back to env `LEGAL_<KEY>`. | A first prod deploy can satisfy the startup check from `.env` before any admin exists. |
| D19 | "My tools" and the editor live in `routers/editor.py`; `routers/me.py` keeps settings, stars and GDPR. | `me.py` was getting too large. |
| D20 | The logo is an SVG recreated from the supplied raster PDF; the wordmark is Roboto Slab (Apache-2.0) glyphs converted to paths. No font file is shipped. | Crisp at any size, dark-mode variant, and no external or self-hosted font needed. |
| D21 | FTS rows use `rowid = tools.id` (the `tool_id` column is kept). | Join on rowid is the fastest FTS5 lookup. |
| D22 | Report spam protection is a honeypot field plus a signed form timestamp (≥ 3 s, ≤ 24 h), no CAPTCHA. | PRD Q6 default; nothing third-party on the page. |
| D23 | Audit entries referring to a deleted user are pseudonymised (`deleted-user-<hash>`) at deletion time; the account row is anonymised immediately and hard-deleted by the purge job after 30 days. | TECH_SPEC §9.5; the address is freed for a fresh sign-up straight away. |
| D24 | Moderators see `/admin` (stats) and `/admin/searches`; every other admin page needs the admin role. | PRD roles table: moderators get "stats only". |
| D25 | Babel extracts `N_()` and `t(lang, msgid)` (keyword `t:2`) in addition to the gettext defaults; run from the repo root (`make i18n`). | Server-side strings rendered in another user's language (owner emails, reason templates) use `t()`. |
| D26 | **Sign-in is email + password; registration is invite-only by default** (`site.registration_open = false`). Magic links and GitHub/Google OAuth are removed (Authlib dropped; tables `oauth_accounts` and `magic_link_tokens` dropped in migration 0002). Passwords: stdlib scrypt (n=2^15, r=8, p=1, salted), ≥ 10 characters; login rate limits per IP and per email; constant work and one generic error for unknown accounts. Recovery: an admin generates a one-time set-password link (48 h); `create-admin` prints one. `ADMIN_EMAILS` may register without an invite. SMTP is optional: without it, notifications stay in the outbox (`/admin/emails`) and authors see status and reasons in "My tools". Terms §3.2/§8.3/§15 and Privacy (authentication data, cookies, providers, retention, security) updated in PT and EN. | Product owner decision (2026-11-16): ship the MVP with no external accounts. Supersedes the PRD F1 sign-in methods. Next steps: TOTP two-factor for moderators/admins, then email (verification, self-service reset). |
| D27 | Admins may publish **their own** pending tool only from the server CLI (`approve-own-tool <slug|id> --as <admin email>`). The audit entry is marked `self_approved: true, via: cli`. The web moderation screens keep refusing self-moderation for everyone. | Product owner decision (2026-11-16): bootstrap the first listings before there is a second moderator, without weakening the PRD F10 rule on the site. |
| D28 | **Portuguese pages are served at the root** (`/`, `/search`, `/t/<slug>`); **English under `/en/`**. Page routers are mounted twice (no prefix and `/en`) with a dependency that fixes the page language; they are registered before the unprefixed action routes so PT paths win. Non-page routes take the language from the referring page, then the cookie, then `Accept-Language`. Only a first visit to `/` from an English browser is redirected to `/en/`. Old `/pt/…` URLs redirect permanently (301; 308 for POST). | Product owner decision (2026-11-16): shorter URLs for the primary language. Supersedes TECH_SPEC §13 (`/{lang}` prefix on all pages). |
| D29 | **Email features switch on with SMTP.** When `SMTP_HOST` is set (or in dev/test): self-service *Esqueceu-se da palavra-passe?* (1 h link, same response for unknown emails, 3/h per email and 10/h per IP), invites emailed when locked to an address, admin *Enviar ligação por email* (48 h), and `cli send-test-email`. Without SMTP these stay hidden and the D26 admin-issued links remain the path. | Product owner decision (2026-11-16): Brevo account available. |
| D30 | **Registration is open by default and verified with a 6-digit code by email; self-service reset uses a code too.** The form asks for name, email, profession, optional specialty, password and terms (PRD F2), so there is no onboarding step afterwards (the handle is auto-suggested and editable in Definições). Nothing is created until the code is entered: a pending sign-up (`email_codes`, password already hashed) lives 15 minutes and is deleted after 24 h. Codes: HMAC-SHA256 with `SECRET_KEY`, 5 tries per code, 2 resends, 3 sign-ups/resets per address per hour. A taken address gets the same next screen plus an "account exists" email to its owner; an unknown address on reset gets a ticket but no email (no enumeration). Open registration requires SMTP; without it registration falls back to invite-only and immediate (D26). Admin-issued set-password links (48 h) stay as links. Terms §3.2 and Privacy (authentication data, retention, security) updated in PT and EN; terms version unchanged (no new obligations). | Product owner decision (2026-11-18), with SMTP working. Implements PRD F1 "anyone can register". |
| D31 | **Reports: the "child sexual abuse material" checkbox is removed; "Material desadequado" (`inappropriate`) is a report reason**, described in the usual *Explicação* field and counted towards auto-hide like dangerous content. Anonymous reporters always give an email; no report type jumps the queue (`reports.csam` dropped in migration 0004). Terms §9.2 no longer promises anonymous CSAM reports. **Tools get an optional public `support_email`**, edited like any other listing field (revisions for published tools) and shown as "Contactar suporte" next to "Reportar problema"; Privacy (published content) updated. | Product owner decision (2026-11-19). Note: DSA Art. 16(2)(c) exempts notices about CSAM offences from the name/email requirement; with this change such reporters can still write to the contact address, but the form asks for an email. Revisit if a lawyer advises restoring the exemption. |
| D32 | **Suggestions to authors.** "Sugerir melhoria" (before "Reportar problema") opens `/t/<slug>/suggest` for signed-in users (not on their own tools): type (feature / improvement / other), message (20–2 000) and an unticked box to share their email. The author gets an email (`Reply-To` = sender only with that consent; new `email_outbox.reply_to`) and an entry in `/me/notifications`, with an unread count on a bell in the header; opening the page marks them read, and the author can delete them. 10 per day per sender, 3 per day per sender and tool. Kept 1 year; included in export; deleted with either account. Not moderated (private messages); abusive ones can be reported through the contact address. Privacy §3–5 and §9 updated. The "opens an external site" note under the tool buttons is removed. | Product owner decision (2026-11-19). Signed-in only to keep spam off authors' inboxes; consent unticked by default (GDPR). |
| D33 | **Profile photos and public profiles.** Optional photo uploaded in Definições (PNG/JPEG/WebP ≤ 2 MB), re-encoded like screenshots: EXIF/metadata dropped, centre-cropped square, 256 px WebP in `media/avatars/<user id>/` with a new random name per upload (the old file is deleted). Shown instead of the initial everywhere (`m.avatar` macro). Admins can remove a photo with a reason (audited, emailed). **`/u/<handle>`** shows photo, name, profession, specialty, role badge (moderator/admin), GitHub, join date and the person's published/archived tools; workplace and email stay private. Visible for active, onboarded accounts (404 otherwise); `noindex` without published tools; authors with published tools are in the sitemap. Photo included in the export and deleted with the account. Privacy §3–5 updated. | Product owner decision (2026-11-19). Supersedes the PRD's "no public profile page in MVP". |
| D34 | **CSAM back as a report reason (amends D31).** "Material de abuso sexual de crianças" (`csam`) is an option in *Motivo*. Choosing it clears and disables the email field (JS; a note explains the report is anonymous), and the server discards any email sent with that reason, so it holds without JS. These reports go to the top of the moderation queue; they follow the normal auto-hide rule (not instant hiding, to avoid abuse). Terms §9.2 and Privacy restored accordingly (migration 0007). | Product owner decision (2026-11-19). Restores the DSA Art. 16(2)(c) option to report CSAM without identification. |
| D35 | **Estatísticas for moderators and admins at `/stats`**: *Visão geral* (former admin dashboard), *Pesquisas* (former `/admin/searches`, now a 301 redirect) and *Categorias* (new: per category, published tools and stars, plus views, search clicks and link opens in 7/30/90 days from `tool_daily_stats`). Linked from the account menu for moderators. Category *management* stays admin-only in Administração; `/admin` now opens Utilizadores for admins and forwards moderators to `/stats`. Queries in `services/site_stats.py`. | Product owner decision (2026-11-19). |
| D36 | **Notifications for moderation decisions and moderators' to-dos (extends D32).** Approving, requesting changes, rejecting, hiding or making a tool visible again, and approving or rejecting an edit, also post an entry (new `notifications` table, migration 0008) to the owner's `/me/notifications`, with the moderator's message (reason or suggestions); the email is unchanged. Entries and suggestions share one feed, newest first; opening the page marks both read; the owner can remove entries. For moderators and admins the page starts with *Por fazer*: new tools, edits and open reports they can act on (their own tools excluded), counted live from the queue rather than stored, so they never go stale. The header bell is replaced by a red count on the account avatar (unread entries + unread suggestions + to-dos), on every screen size. Kept 1 year; in the export; deleted with the account. Privacy §9 updated. | Product owner decision (2026-11-19). |
| D37 | **Editorial texts live in `content/` as Markdown, one folder per page, `<name>.md` (PT, prevails) beside `<name>_en.md` (EN).** Covers the home page blocks, page intros (categories, blog, report, suggest, notifications, stars, my tools, submit, onboarding, delete account), About/Contact (`about/`, `contact/`), the legal pages (`legal/`), blog articles (`blog/<slug>.md`, replacing `blog/{pt,en}/`) and every email (`emails/<name>.md`, replacing `templates/emails/*.txt`; amends D15). Front matter is plain `field: value` lines (no YAML quoting); bodies are Markdown, rendered with the trusted sanitiser. Templates read blocks with `site_text("home/hero")` (`.title`, `.html`, `.inline`); `{{ name }}` in a body is filled with an escaped value. Emails are Jinja text (`subject:` + body, `{% if %}`, `{% include "_statement.md" %}`) rendered by their own loader into `emails/_layout.html`. A missing `_en.md` falls back to PT at runtime and fails `tests/test_content.py`. Buttons, labels, errors and flash messages stay in the gettext catalogue. Editing guide: `content/README.md`. | Product owner decision (2026-11-20): let the team edit site texts without touching templates. |
| D38 | **First-visit notice.** Until a visitor accepts, every page opens with a blocking notice (`partials/notice.html`, text in `content/notice/notice.md`): gitmgf is an aggregator that only shows what each author published, and each tool is its creator's sole responsibility; links to the Terms and Privacy Policy (new tab) and an *Aceitar e continuar* button. Without JS a fixed overlay covers the page and the form posts to `/notice/accept` (CSRF-protected, returns to a safe `next`); with JS it becomes a modal `<dialog>` (background inert, Esc ignored) accepted by `fetch` without a reload. Acceptance is the `gitmgf_notice` cookie (HttpOnly, 1 year) holding the Terms version, so a new Terms version asks again. Signed-in users (who accepted the Terms at registration) and the Terms, Privacy and Disclaimer pages skip it. Treated as strictly necessary (it only remembers the visitor's own acknowledgement); Privacy §6 cookie table updated in PT and EN. | Product owner decision (2026-11-20), for liability. |
| D39 | **The site addresses users as "tu".** UI strings (gettext msgids), editorial texts in `content/`, emails and the certification help texts in `seeds/certifications.yaml` use second-person "tu" (*Submete a tua ferramenta*, *Já tens conta?*, *Indica um email válido*) instead of formal or impersonal forms; buttons and labels stay in the infinitive. Third-person references to other people (*Ainda não publicou ferramentas* on someone's profile) are unchanged. The legal pages (Terms, Privacy, Submission Guidelines, Disclaimer) are not part of this change. English texts unchanged. Supersedes the CLAUDE.md "impersonal forms" tone rule. | Product owner decision (2026-11-23): the audience (clinicians, mostly residents and peers) is comfortable with "tu", which reads closer and matches the blog. |
| D40 | **Moderators and admins don't feed popularity.** Views, search clicks and link opens by a signed-in moderator or admin are not recorded on any tool, on top of the existing rule that owners (any role) never count on their own tools. Decided in `permissions.counts_towards_usage()`, used by `tracking.record()`. Stars are unchanged (owners still can't star their own tools). Visits made while signed out can't be told apart and still count. `cli purge-staff-events` deletes past events by current moderators/admins, rebuilds the affected `tool_daily_stats` rows and recomputes scores (audited); raw events are kept 180 days, so older daily totals can't be corrected. | Product owner decision (2026-11-23): the team opens listings constantly while testing and moderating, which inflated scores and is a conflict of interest. |
